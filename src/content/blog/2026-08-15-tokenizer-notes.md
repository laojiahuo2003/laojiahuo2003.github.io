API 按 token 计费，上下文窗口按 token 算，连"模型支不支持中文"的第一道坎都在 tokenizer。这是最靠近钱的一层基础设施，值得单独一篇笔记。

## Tokenizer 是什么

模型不读字符，读 token ID。tokenizer 是字符和整数之间的双向翻译：编码时把文本切成 token（词表里的编号），解码时拼回来。**它是训练前冻结的外挂**——模型训练完，词表就焊死了，加一个新 token 都要动 embedding 层。

## BPE：从字节拼出词

主流方案 BPE（Byte Pair Encoding）的训练过程朴素得可爱：

```text
1. 把语料拆成最小单位（字节）
2. 数一数：哪两个相邻单位总是连在一起？
3. 把出现最多的一对合并成新 token，进词表
4. 回到 2，重复几万次
```

结果是一个**频率驱动的词表**：常见词（the、的、ing）整个占一个 token，生僻内容退回字节拼。这解释了 tokenizer 的所有行为——它不是懂语言，只是记住了统计。

**byte-level** 是关键设计：基础单位是字节而不是字符，所以任何 UTF-8 文本都能编码，永远不会有"无法表示"——最多是贵（一个汉字 3 字节，切得碎就烧 3 个 token）。

## 为什么中文更贵

在以英文为主的语料上训 BPE，合并的优先级自然偏向英文模式："the" 早早就合成一个 token，而"熵"可能到几万次合并后还没轮上，只能按字节拆成 3 块。

同样意思的一句中英文，中文的 token 数常是英文的 1.5-2 倍——**同价不同量**，这就是很多"中文按 token 计费更贵"的底层原因。词表规模和语料配比才是案发现场。

我的验证方法很土但有效：拿各家官网的 tokenizer 试玩页，同一段话来回编码，数 token——差异大到值得每个常写中文的人都知道。

## 词表大小是个权衡

词表越大：常见多字词能整个表示（中文友好、序列更短），但 embedding 矩阵更大、低频 token 训练不充分（用到就是冷启动）。经典规模 3-5 万（LLaMA 32k），新词表往 10-20 万走（o200k、Qwen 系）。

## o200k 改进了什么

GPT-4o 时代换的词表（o200k，约 20 万 token），方向就是上面这些账：更大词表吃下更多多字节文字和代码模式，同样的文本 token 数更少——**推理成本直接打折**，多语言场景尤其明显。换词表意味着重训 embedding，所以模型不轻易换——换了的都是算了大账的。

## 一个冷知识收尾

"strawberry 有几个 r" 这类问题的锅也常在 tokenizer：模型看到的不是字母序列，是一个或几个 token ID——它真的"看不见"那几个 r。数错不是不会数，是没拿到原料。
